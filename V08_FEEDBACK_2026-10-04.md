## New highest-priority feedback

### 1. Persistent bottom game bar
The user does not want to open a full MENU for routine play.

Desired screen hierarchy:
1. game world
2. persistent bottom management/menu bar
3. live event log/ticker directly above the bar

The bar should contain the current important management actions instead of hiding them in a modal menu.

Minimum quick actions:
- GUILD UP
- HIRE
- facility/building management entry
- record/save entry

Secondary navigation can include Guild / Adventurers / Quests / Facilities / Record, but should open a compact bottom sheet rather than a full-screen modal.

### 2. Live log at bottom
Existing runtime messages should flow near the bottom of the screen, immediately above the persistent management bar.

Examples:
- quest complete
- adventurer returned
- resources gained
- upgrade complete
- hire result

Do not cover the center of the world with toast spam.

### 3. Building upgrades from bottom UI
The previous "inspect building" interaction has weak purpose if routine upgrades require extra taps.

Desired behavior:
- building tap can select/focus a building
- the bottom bar/sheet becomes contextual for that building
- upgrade action should be available from the bottom UI
- detailed building screens can come later

v0.8 can begin with Guild Hall + facility list if per-building state API is not yet available.

### 4. Mobile movement = drag, NOT tap-to-destination
The user explicitly rejected tap-to-destination as the primary mobile control.

Required feel:
- touch field
- drag relative to touch origin to choose movement direction
- player keeps stepping while the finger is held/dragged
- release = stop after the current short tile step
- no permanent joystick art
- no tap-to-auto-walk route on plain field taps
- building tap may remain a separate contextual interaction if it does not conflict with drag

### 5. Population cap = 200
The old 10-person cap is rejected.

Required system change:
- max roster 200
- save/load must accept up to 200
- HIRE display uses current / 200
- do not instantly spawn 200 visible actors on screen
- simulation population and rendered population may be decoupled for performance

Visual principle:
**population growth should feel meaningful without turning the approved town into a crowd blob.**

### 6. Game speed must be scarce
Current ×5 / ×10 always-available speed destroys the feeling of growth.

Required:
- normal = ×1
- maximum = ×3
- speed above ×1 requires a consumable/limited boost item or timed entitlement
- no permanent free ×5 / ×10
- when boost expires, return to ×1

Suggested prototype item name: `砂時計 / HOURGLASS`
Exact economy/balance can change later.

### 7. Typography
All visible UI labels, numbers and Japanese text should share one consistent 2D-digital / 16-bit-inspired rhythm.

Avoid:
- mixed system-font feeling
- generic rounded mobile app buttons
- text that looks pasted on top of the game

### 8. Autosave is mandatory
The user observed that reloading the browser starts from the beginning.

Required:
- save automatically and continuously
- save on meaningful mutations: hire / upgrade / construction / gacha / item use / reward claim
- heartbeat save at least every 1–2 seconds in prototype
- save on `visibilitychange`, `pagehide`, `beforeunload` and app background/freeze where supported
- load newest valid save at boot before normal play
- keep a manual "record/save" action as visible confirmation, but do not rely on it
- maintain a backup/mirror save record so a malformed current save does not erase all progress
- future app build should map this abstraction to native persistent storage without changing game-state schema

### 9. New building construction
The game needs long-term town growth, not only upgrades to existing buildings.

Required system:
- empty building slots / plots
- choose a building type
- pay materials/currency
- construction timer or instant prototype build
- completed building becomes part of persistent town state
- building can then be upgraded

Initial candidate buildings:
- 薬草園 / HERB GARDEN
- 訓練所 / TRAINING HALL
- 工房 / WORKSHOP
- 交易所 / TRADING POST

Each building must have a clear mechanical purpose rather than being decoration only.

### 10. Item drops / rarity / gacha / future monetization hooks
The prototype should have a deeper collection loop, but **real-money purchase is not required yet**.

Required prototype concepts:
- rare item drops from completed quests
- rarity tiers
- inventory
- consumable speed items
- gacha/summon with transparent prototype rates
- a premium/secondary currency placeholder
- system architecture that can later connect to app IAP without rewriting the game loop

Suggested initial rarities:
- N / Normal
- R / Rare
- SR / Super Rare
- SSR / Special Rare

Suggested prototype drops:
- 砂時計 / Hourglass → temporary ×2/×3 speed entitlement
- 召喚券 / Summon Ticket → one gacha draw
- 建築設計図 / Blueprint → new building construction
- 星晶 / Gem → secondary/premium-currency placeholder

Initial rule:
- these can drop during ordinary play
- no paywall required for core progression
- paid acquisition can be added later at app stage

### 11. Long-term progression hooks
Add grind/collection depth gradually:
- building collection and levels
- adventurer rarity / class / traits
- item inventory and rare drops
- quest difficulty tiers
- guild rank / reputation
- collection book / records
- milestone rewards

Do not implement all screens at once. First make the underlying state persistent and expose only the smallest playable loop.
